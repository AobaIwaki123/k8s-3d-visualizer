# 並列タスクドキュメント作成ガイドライン

並列タスクをエージェントに割り当てるドキュメントを書く際に守るべきルール。

## Rule 1: タスクはディレクトリで分割し、ファイルを渡すだけで実装できるようにする

**WHY:** 並列エージェントは互いの作業を知らない。ファイルパスと依存関係が明示されていなければ、衝突・重複・抜け漏れが起きる。

**WHY NOT 「共有ファイルを直接編集させない」:** 複数エージェントが同一ファイルを同時編集すると競合が確実に発生する。担当ファイルを 1:1 で割り当てることで競合ゼロを保証できる。

**追加ルール（厳守）:**
- **共有ファイル（`poc.js`, `App.js`, `main.js` 等）の「同時」編集禁止**: 複数の並列エージェントに同一ファイルを同時に編集させてはならない。
- **インターフェースの先行提供**: 並列タスクを開始する**前**に、メインエージェントが共有ファイルに必要なフックやインターフェース（例：レイヤー登録用の配列やイベントリスナー）を追加しておくことは推奨される。これにより、各エージェントは共有ファイルを触ることなく、自身の担当ファイルのみに集中できる。

## Rule 2: 統合（Integration）は「インターフェース」を介して行う

並列タスクがスムーズに進むよう、メインエージェントは以下の手順を踏む。

1. **設計フェーズ**: 共有ファイルにどのような変更が必要か設計する。
2. **準備フェーズ（フォアグラウンド）**: メインエージェント自身が共有ファイルを編集し、並列タスクが利用できる「受け皿（インターフェース）」を定義・実装する。
3. **並列フェーズ（バックグラウンド）**: サブエージェントを起動し、準備されたインターフェースを利用して各機能を独立したファイルとして実装させる。
4. **最終調整フェーズ**: 必要に応じて、メインエージェントが最終的な繋ぎ込みを行う。

**WHY:** 最初に「疎結合な設計」を行うことで、並列作業の衝突を防ぎつつ、スピードを最大化できる。

## Rule 3: 実装者は必ずブランチを切り、PR を作成する

**WHY:** main への直 push は並列作業では衝突リスクが高い。PR を経由することで、統合時のコンフリクト解決と差分レビューが可能になる。

**WHY NOT 「main に直接 push」:** 並列タスクが同時に main を変更すると、後から push した側が先行変更を上書きする危険がある。

**実装者への指示テンプレート:**
```
ブランチ名: task/<task-name>
PR タイトル: [Task X] <実装内容の一行要約>
PR 作成後に URL を報告すること
```

## Rule 3: 環境操作（npm install 等）は指示がない限り行わない

**WHY:** 実行環境はエージェントが知らない制約（オフライン・CI・権限制限など）を持つ場合がある。指示なしの環境操作はユーザーの意図しない副作用を生む。

**WHY NOT 「動作確認のために install する」:** 動作確認が不可能な環境でも実装は完成できる。コードの正しさは型・仕様・インターフェース整合性で担保し、実行確認はユーザーに委ねる。

**デフォルト動作:**
- 実装（ファイル編集）: 実施する
- `npm install` / `pip install` / `docker build` 等: **指示があるときのみ実施する**
- `npm run dev` / テスト実行: **指示があるときのみ実施する**

## Rule 4: 勝手に実装に入らない（調査・設計ドキュメント作成のみ）

**WHY:** スキル発動時の初期段階は「Inquiry（調査・設計）」フェーズである。ユーザーの合意なしに実装（ファイルの書き換え）を開始すると、設計ミスがあった場合の修正コストが高くなる。

**動作ルール:**
- このスキルが適用されるタスクは、原則として**ドキュメントの作成（調査報告やタスク定義）まで**をスコープとする。
- コードの修正や新規作成などの「実装（Execution）」フェーズに進むには、ユーザーからの明示的な指示（Directive）を待つこと。
- 提案したドキュメントや設計方針に対して、ユーザーから「実装して」「進めて」などの承認が得られてから実装を開始する。
