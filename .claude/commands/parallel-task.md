# 並列タスクドキュメント作成ガイドライン

並列タスクを Claude に割り当てるドキュメントを書く際に守るべきルール。

---

## Rule 1: タスクはディレクトリで分割し、ファイルを渡すだけで実装できるようにする

**WHY:** 並列エージェントは互いの作業を知らない。ファイルパスと依存関係が明示されていなければ、衝突・重複・抜け漏れが起きる。

**WHY NOT 「共有ファイルを直接編集させない」:** 複数エージェントが同一ファイルを同時編集すると競合が確実に発生する。担当ファイルを 1:1 で割り当てることで競合ゼロを保証できる。

**ドキュメントに必須の記載:**
- `## 担当ファイル` — 実装するファイルパスを明示
- `## 依存ライブラリ` — 使ってよい import 元を限定
- `## export するインターフェース` — 他タスクとの結合点を型で固定
- `## 完了条件` — 実装完了の判定基準

---

## Rule 2: 実装者は必ずブランチを切り、PR を作成する

**WHY:** main への直 push は並列作業では衝突リスクが高い。PR を経由することで、統合時のコンフリクト解決と差分レビューが可能になる。

**WHY NOT 「main に直接 push」:** 並列タスクが同時に main を変更すると、後から push した側が先行変更を上書きする危険がある。

**実装者への指示テンプレート:**
```
ブランチ名: task/<task-name>
PR タイトル: [Task X] <実装内容の一行要約>
PR 作成後に URL を報告すること
```

---

## Rule 3: 環境操作（npm install 等）は指示がない限り行わない

**WHY:** 実行環境はエージェントが知らない制約（オフライン・CI・権限制限など）を持つ場合がある。指示なしの環境操作はユーザーの意図しない副作用を生む。

**WHY NOT 「動作確認のために install する」:** 動作確認が不可能な環境でも実装は完成できる。コードの正しさは型・仕様・インターフェース整合性で担保し、実行確認はユーザーに委ねる。

**デフォルト動作:**
- 実装（ファイル編集）: 実施する
- `npm install` / `pip install` / `docker build` 等: **指示があるときのみ実施する**
- `npm run dev` / テスト実行: **指示があるときのみ実施する**
